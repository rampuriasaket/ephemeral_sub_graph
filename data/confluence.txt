PAGE: Auth Service Outage Postmortem — August 2026
SPACE: Engineering / Postmortems
AUTHOR: Priya Nair
LAST UPDATED: 2026-08-02
LABELS: postmortem, auth-service, incident-review
RELATED: INC1042, PROJ-201, PR-455
--------------------------------------------------------------------
BODY:
On 2026-08-01, auth-service experienced a ~2.5 hour period of
degraded login availability due to an expired JWT signing key that
was not rotated ahead of its expiry window (INC1042). Impact: an
estimated 60% of login attempts failed during the affected window.

Root cause: the signing key rotation process was manual and relied on
a calendar reminder that was missed. Resolution: the key was rotated
manually, restoring service within minutes, and a follow-up story
(PROJ-201) added automated expiry alerting, shipped in PR-455.

Action items:
1. (Done) Add automated expiry alerting for all signing keys used by
   auth-service, not just this one.
2. (Open, unassigned) Audit other services for similarly manual key
   rotation processes that could fail the same way.
3. (Done) Update on-call runbook with signing-key rotation steps.

PAGE: Payment Gateway Troubleshooting Guide
SPACE: Engineering / Runbooks
AUTHOR: Marcus Webb
LAST UPDATED: 2026-07-20
LABELS: runbook, payment-gateway, troubleshooting
RELATED: (general guide — not tied to a specific incident number)
--------------------------------------------------------------------
BODY:
This page covers common failure modes for payment-gateway and how to
triage them. Symptoms of connection pool exhaustion under load include
elevated request latency, intermittent timeouts concentrated during
peak traffic windows, and connection-refused errors in the
payment-gateway logs once the pool is fully saturated.

Standard triage steps: check current pool utilization against
configured max size, check for any recent deploys that changed
connection handling, and check whether a downstream dependency
(fraud-check-service or the external payment processor) is
responding slowly, which can cause connections to be held open
longer than expected and exhaust the pool indirectly.

Note: this guide will be updated with more specific guidance once the
current investigation into intermittent payment-gateway timeouts
concludes.

PAGE: Order Service On-Call Runbook
SPACE: Engineering / Runbooks
AUTHOR: Diego Alvarez
LAST UPDATED: 2026-05-15
LABELS: runbook, order-service, on-call
RELATED: INC0980
--------------------------------------------------------------------
BODY:
Known failure pattern: order-service database connection pool
exhaustion. This has occurred previously (see INC0980, May 2026) when
a long-running batch reconciliation job held connections open for an
extended period, starving the pool for regular request traffic.

Immediate mitigation steps if this recurs:
1. Check for any currently running batch jobs against order-service's
   database and kill them if they are holding connections abnormally
   long.
2. If pool exhaustion persists, manually increase the connection pool
   ceiling as a temporary measure and page the Order Platform team.
3. File a ticket to investigate a permanent fix — as of this writing,
   no permanent code fix has been merged; the pool ceiling increase
   from the May incident was a manual, undocumented mitigation only.

PAGE: Notification Service Architecture
SPACE: Engineering / Design Docs
AUTHOR: Chen Liu
LAST UPDATED: 2026-06-10
LABELS: architecture, notification-service, design-doc
RELATED: (general design reference)
--------------------------------------------------------------------
BODY:
This document describes the architecture of the notification
delivery pipeline. Messages are produced onto a queue by upstream
services (order-service, shipping-service) and consumed by a pool of
notification-worker processes, which format and dispatch the actual
push notification via the external push-notification-provider
integration.

Consumer concurrency is currently fixed at a static pool size,
configured in notification-queue-config. This was set based on
expected traffic at initial launch and has not been revisited since,
which may become a scaling bottleneck as message volume grows. Worth
revisiting if queue depth or delivery latency ever trends upward over
time.

PAGE: Checkout Idempotency Design Doc
SPACE: Engineering / Design Docs
AUTHOR: Aisha Rahman
LAST UPDATED: 2026-08-09
LABELS: design-doc, checkout-service, idempotency
RELATED: PROJ-301, PR-601
--------------------------------------------------------------------
BODY:
Following INC1101 (customers double-charged during a checkout retry),
this document describes the idempotency-key pattern adopted for
checkout-service's payment retry logic. Each checkout attempt
generates a unique key stored alongside the checkout session; if a
retried request arrives with the same key, payment-gateway is
instructed to treat it as a duplicate rather than a new charge.

Keys are retained for 24 hours after checkout completion, long enough
to cover any reasonable retry window without indefinitely growing
storage. Other services making retryable payment-adjacent calls
(refunds, subscription renewals) should adopt the same pattern; this
is not yet enforced automatically.

--------------------------------------------------------------------
BODY:
This runbook was written ahead of the payment gateway migration
project to capture known risk areas. Chief among them: any webhook
handler that parses the gateway's payload format needs explicit
review during migration, since a silent parsing mismatch (rather than
a loud error) is the most likely way a handler could break without
being immediately noticed. Refund and subscription-renewal webhook
handlers are specifically called out as worth double-checking, given
how infrequently their code paths are exercised compared to the main
payment flow.

PAGE: Email Deliverability Runbook
SPACE: Engineering / Runbooks
AUTHOR: Chen Liu
LAST UPDATED: 2026-08-12
LABELS: runbook, notification-service, deliverability
RELATED: PROJ-410, INC1215
--------------------------------------------------------------------
BODY:
Covers common causes of email deliverability problems: DNS/DKIM
misconfiguration after domain changes, sender reputation issues with
specific providers, and content-based spam filtering. Provider-specific
filtering (as seen with Gmail in INC1215) is called out specifically —
some providers validate DKIM more strictly than others, so a broken
record can silently affect only a subset of recipients rather than
everyone, which makes it easy to miss without provider-segmented
delivery metrics. This page was prompted partly by an earlier,
still-open investigation into a broader delivery-rate drop that hadn't
been narrowed to a single cause at the time of writing.

PAGE: Email Delivery Service — Operational Runbook
SPACE: Engineering / Runbooks
AUTHOR: Sam Okafor
LAST UPDATED: 2026-08-17
LABELS: runbook, email-delivery-service, operations
RELATED: (none — general operational reference, not tied to a specific incident)
--------------------------------------------------------------------
BODY:
This page is the on-call reference for email-delivery-service, which
handles all outbound transactional email (password resets, order
confirmations, shipping updates) via a third-party email provider.

WHAT TO CHECK FIRST:
If delivery times look elevated, check the provider-side queue depth
dashboard before assuming the problem is in our own service --
several past delays have turned out to be a backlog on the provider's
side rather than anything wrong with email-delivery-service itself.
In those cases there is usually nothing to fix on our end; the queue
clears on its own once the provider catches up, and the only action
needed is keeping support informed so they can reassure customers
asking about delayed password-reset emails.

If the provider-side dashboard looks normal but delivery is still
slow, escalate to the Data Platform on-call to check
email-delivery-service's own outbound queue instead.
